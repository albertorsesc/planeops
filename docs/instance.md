# Your instance

`plane init` creates an **instance**: a directory that is yours, not the tool's.
Treat it like a dotfiles repo: `git init` it, commit it, keep it with your
projects if you like. Init asks where (Enter accepts the default, or type any
valid path: hidden directories included).

```
~/planeops/
├── .planeops           marker: this directory is an instance
├── registry/           desired state: the YAML entries you declare, edit, and prune
├── instance.yaml       this machine's adapter settings (paths your tools use)
├── secrets.sops.yaml   encrypted values, if you use the secrets store
└── observed/<host>/    generated per machine: snapshot.json, DRIFT.md, DRIFT.json
```

## What you own vs what is generated

You own `registry/` and `instance.yaml`: they ARE your setup's documentation.
`observed/` is regenerated by every scan; gitignore it, or commit it if you want
drift history in your log.

## Several machines, one instance

One instance can serve several machines: entries say which `hosts:` they apply
to, and each machine writes its own `observed/<host>/` directory, so scans never
collide.

## The tool's exact footprint

planeops's whole footprint on a machine is three things:

1. The program itself (your package manager's territory).
2. This instance directory.
3. Only when the instance lives somewhere custom: a one-line pointer in
   `~/.config/planeops/config.toml` recording where.

Every one of those writes is announced when it happens; declining any
confirmation writes nothing.

## How commands find the instance

Resolution order: `--repo` flag, then `$PLANEOPS_INSTANCE`, then the
`~/.config/planeops/config.toml` pointer, then walking up from the current
directory looking for the `.planeops` marker. An unmarked directory is refused:
only `plane init` creates instances, so a stray command can never scaffold state
somewhere you did not choose.
